# ToDo

ფერადი ნოტები და ჩეკლისტები, რომლებიც ინტერნეტის გარეშეც მუშაობს. PWA: ბრაუზერიდან მთავარ ეკრანზე ინსტალდება და ცალკე აპივით იხსნება. ყველა ნოტა ინახება მხოლოდ მოწყობილობაზე (IndexedDB), სერვერი არ არის საჭირო.

## ფუნქციები

- **ჯგუფები**: ზედა ზოლში პატარა ბარათები (ხატულა, სახელი, ნოტების რაოდენობა). ჯგუფის არჩევისას მხოლოდ მისი ნოტები ჩანს; ჯგუფს აქვს სახელი, ხატულა და ფერი. ნოტი ჯგუფს ირჩევს რედაქტორში, ზედა ეტიკეტიდან. ჯგუფის წაშლისას ნოტები რჩება
- ტექსტური ნოტები და ჩეკლისტები; **ერთ ნოტაში ორივე ერთად** (ტექსტს ჩეკლისტი ემატება და პირიქით). `kind` მხოლოდ მინიშნებაა, ბარათი, გაზიარება, ძებნა და სინქრონიზაცია შინაარსს ეყრდნობა. თუ ნოტაში მხოლოდ ერთია, ზედა ზოლში „გარდაქმნა“ (ტექსტი ↔ ჩეკლისტი) გვაქვს
- 8 ფერი, ფერით გაფილტვრა და ფერით დახარისხება
- ძებნა, მიმაგრება, ნაგავი (აღდგენით და "დაბრუნებით"). წაშლილი ნოტა ნაგავში **30 დღე** ინახება და მერე თავისით, სამუდამოდ იშლება (შემოწმება აპის გახსნისას და ეკრანზე დაბრუნებისას). ვადა იცვლება `src/features/notes/trash.ts`-ში
- **ბმულები**: ნოტაში ჩაწერილი ან ჩასმული ვებ-მისამართი (და Google Maps ბმული) ავტომატურად ამოიცნობა. რედაქტორში ჩანს ღილაკი, ჩეკლისტის ხაზზეც, სიაში კი, თუ ნოტაში ერთი ბმულია, ბარათიდან ერთი შეხებით იხსნება ახალ ჩანართში (Maps ბმული — ტელეფონის შეხედულებით Maps აპში)
- **გაზიარება**: ნოტაში ღილაკი ხსნის ტელეფონის გაგზავნის მენიუს (WhatsApp, Viber, SMS...). ჩეკლისტი იგზავნება ☐ / ☑ ხაზებად. თუ მენიუ არ არის (მაგ. კომპიუტერზე), ტექსტი კოპირდება
- **კალენდარი** (`src/features/calendar/`): ნოტას შეიძლება ჰქონდეს თარიღი (`date`, დღე „2026-10-30“; რედაქტორში ჩიპი „თარიღი“: დღეს / ხვალ / ერთ კვირაში / ნებისმიერი დღე / მოხსნა). კალენდარის ტაბი აჩვენებს თვეს (ორშაბათიდან), დღეებზე ნოტის ფერის წერტილებით; დღეზე დაჭერა ხსნის ამ დღის ნოტებს, „+“ ქმნის ახალს ამ თარიღით. თარიღი სინქრონიზდება და ინახება ასლებშიც. ჯერ მხოლოდ დღეა (დრო/შეხსენება არა)
- **არქივი მოხსნილია** (ნაგავი 30 დღეს ინახავს). ძველად დაარქივებული ნოტები ჩვეულებრივ სიაში ჩანს, `archived` ველი მონაცემებში რჩება მხოლოდ თავსებადობისთვის
- **ნავიგაცია**: აპი ყოველთვის ნოტებზე იხსნება. კალენდარი, ნაგავი და პარამეტრები ნოტებზე "ზემოდან იხსნება": იმავე ღილაკზე მეორედ დაჭერა ან ტელეფონის "უკან" ხურავს და ნოტებს აბრუნებს (`src/app/tabNav.ts`)
- ბექაპი JSON ფაილით, ჯგუფებიანად (ჩამოტვირთვა და აღდგენა, ახალი/ძველი ვერსიის გაერთიანებით; ძველი ფორმატის ფაილებიც იკითხება)
- ქართული და ინგლისური, ნათელი / ბნელი / სისტემური თემა
- ავტომატური შენახვა: ტექსტი არ იკარგება, თუნდაც ბექი ან სხვა აპზე გადასვლა მაშინვე დააჭირო

შეგნებულად არ არის: შეხსენებები და ვიჯეტი (PWA-ს ეს ვერ აკეთებს საიმედოდ), სინქრონიზაცია (მომზადებულია, იხ. ქვემოთ).

## სტრუქტურა

```
src/
  app/            აპის გარსი: routes, ქვედა ნავიგაცია, თემა, განახლების შეტყობინება
  core/           საერთო ნაწილი, ფუნქციებზე დამოუკიდებელი
    db/           Dexie ბაზა და სქემის ვერსიები
    i18n/         ენები (languages.ts + locales/*.json)
    settings/     პარამეტრები (ენა, თემა, ხედი), localStorage-ში
    ui/           პატარა საერთო კომპონენტები
  features/       თითო ფუნქცია = ერთი საქაღალდე
    notes/        მოდელი, repository, სელექტორები, კომპონენტები, გვერდები
    groups/       ჯგუფების მოდელი, repository, ზოლი (GroupStrip), ჯგუფის ფურცლები
    backup/       ბექაპის ფორმატი და აღდგენა
    settings/     პარამეტრების გვერდი
```

წესები, რომ აპი გაფართოვდეს და არ დაიბნეს:

- **ბაზასთან მხოლოდ `repository` საუბრობს.** კომპონენტები `db`-ს პირდაპირ არ ეხებიან (`features/notes/repository.ts`).
- **სუფთა ლოგიკა ცალკეა** (`model.ts`, `selectors.ts`): ფილტრი, დახარისხება, ვალიდაცია. ტესტებით დაფარულია.
- **ფუნქცია არ იმპორტირებს სხვა ფუნქციას**, მხოლოდ `core`-ს. გამონაკლისები: `groups` და `backup` იყენებენ `notes`-ს (ის ძირითადი ფუნქციაა).
- **ბაზის ცვლილება = ახალი `this.version(n)`** `core/db/db.ts`-ში. ძველ ვერსიას ხელს არ ვუხლებთ. ვერსია 2 (ჯგუფები) უკვე ასე დაემატა და ძველ ნოტებს `groupId = null` ენიჭებათ; ეს ტესტითაა დაფარული.

პარამეტრებში ენის არჩევანი თავისით გაჩნდება.

## სინქრონიზაციისთვის მომზადებული ადგილები

- ყველა ჩანაწერს აქვს UUID (`id`), `createdAt`, `updatedAt` და `deletedAt`.
- წაშლა ჯერ მხოლოდ ნიშნავს ჩანაწერს (`deletedAt`), რაც მერე tombstone-ად გამოდგება.
- `repository.importMany` უკვე აერთიანებს ჩანაწერებს `updatedAt`-ით: უახლესი იგებს. იგივე წესი გამოგადგება ღრუბელთან გასაერთიანებლად.
- ფიზიკური წაშლა (`deleteForever`, `emptyTrash`) სინქრონიზაციის დამატებისას tombstone-ით უნდა შეიცვალოს (მონიშნულია კოდში).
- დაშიფვრა (end-to-end) ცალკე გადაწყვეტილებაა, სანამ ნოტებს ღრუბელში ვინახავთ.

## ანგარიში და სინქრონიზაცია (Firebase)

Firebase პროექტი: `todo-f1950` (Authentication: Google და ელფოსტა/პაროლი; Firestore: europe-west3; უფასო Spark გეგმა, ბარათი არ არის მიბმული). კონფიგურაცია `src/core/firebase/config.ts`-შია (საჯარო იდენტიფიკატორებია და არა საიდუმლო), მონაცემებს წესები იცავს: `docs/firestore.rules` (ყველა ანგარიში მხოლოდ საკუთარ `users/{uid}/...`-ს ხედავს).

გეგმა: 1) ანგარიშით შესვლა ✅ · 2) ნოტებისა და ჯგუფების სინქრონიზაცია ✅ · 3) 30-დღიანი დღიური ასლები და აღდგენა ✅ (ტელეფონზე გასამოცდელია).

**როგორ მუშაობს სინქრონიზაცია** (`src/features/sync/`):
- ტელეფონის ბაზა (Dexie) რჩება მთავარი, აპი ოფლაინ მუშაობს. ღრუბელში ინახება `users/{uid}/notes` და `users/{uid}/groups`.
- ყოველ ჩანაწერს აქვს `updatedAt`. **უახლესი იგებს** (`merge.ts`).
- თუ ერთი ნოტის ტექსტი ორივე მხარეს შეიცვალა ბოლო სინქრონიზაციის შემდეგ, დამარცხებული ტექსტი ინახება **ცალკე ასლად** („(ასლი)“ სათაურში), ამიტომ ტექსტი არ იკარგება.
- სამუდამოდ წაშლისას ღრუბელში რჩება მხოლოდ წაშლის ნიშანი (tombstone), ტექსტი იშლება. სხვა მოწყობილობებიც შლიან ნოტას. ნიშანზე გვიან შეცვლილი ნოტა ბრუნდება.
- „რა შეიცვალა“ ეკითხება ღრუბლის საკუთარი დროით (`syncedAt`), და არა ტელეფონის საათით. ამიტომ ხელახლა გახსნისას მხოლოდ ახალი ცვლილებები იკითხება (იაფია).
- თითო ნოტა ერთი დოკუმენტია (ლიმიტი 1 მბ). ძალიან დიდი ნოტა ცალკე ვერ გაიგზავნება, დანარჩენს ეს არ აფერხებს.
- ერთი მოწყობილობა = ერთი ანგარიში: თუ ტელეფონზე სხვა ანგარიშის ნოტებია, არ ვაერთიანებთ და ვთავაზობთ „ბექაპი და გასუფთავებას“.
- ერთდროულად მხოლოდ ერთი ფანჯარა სინქრონიზდება (Web Locks).
- რედაქტორი, რომელშიც ჯერ არაფერი დაგიწერია, სხვა მოწყობილობიდან მოსულ ახალ ტექსტს თავისით აჩვენებს.

ტესტები: `engine.test.ts` ორ „მოწყობილობას“ ერთ ყალბ ღრუბელთან აკავშირებს (ოფლაინ, კონფლიქტი, წაშლა, სხვა ანგარიში, შეცდომები). რეალური Firestore-ის ადაპტერი (`firestoreStore.ts`) თხელია და მხოლოდ ტელეფონზე მოწმდება.

**დღიური ასლები** (`src/features/snapshots/`):
- ასლი იღება **აპის დატოვებისას** (დახურვა ან სხვა აპზე გადასვლა, `visibilitychange`/`pagehide`), და არა დღის განმავლობაში. ის მთელი აპის მდგომარეობაა (ნოტები, ჯგუფები, ნაგავიც), დაკუმშულად (gzip, ნაწილებად ≤ 700 კბ).
- ორი ნაბიჯი: **1) `capture`**: ასლი ჯერ ადგილობრივად ინახება (`pendingSnapshots` ცხრილი) დღევანდელი თარიღით, ინტერნეტი არ სჭირდება; **2) `flush`**: ატვირთვა `users/{uid}/snapshots` + `snapshotChunks`-ში, როცა შესაძლებელია (მაშინვე, ან შემდეგ გახსნაზე/კავშირის დაბრუნებისას). ასლი **ინარჩუნებს იმ დღის თარიღს, როცა გაკეთდა**, თუნდაც მოგვიანებით აიტვირთოს.
- ერთი დღე = ერთი ჩანაწერი: იმავე დღის შემდეგი ასლი ცვლის წინას, ამიტომ დღე ინახავს **თავისი დღის ბოლო მდგომარეობას**. თუ არაფერი შეცვლილა, ახალი ასლი არ იქმნება. ასლი არ იქმნება, სანამ ეს მოწყობილობა ერთხელ მაინც არ დასინქრონდა (ნახევრად ჩატვირთული მდგომარეობა არ ინახება).
- **ინახება ბოლო 30 ასლი რაოდენობით და არა ასაკით**: ახალზე ყველაზე ძველი იშლება. აპს თვეობით თუ არ გამოიყენებ, არაფერი იშლება. „აღდგენამდე“ საგარანტიო ასლები ცალკე ითვლება (ბოლო 5).

## ვერსია

Settings → "აპის შესახებ" აჩვენებს ორ რამეს: **ვერსიას** (`package.json`-ის `version`, ხელით იცვლება ყოველ გამოშვებაზე) და **აგების კოდს** (git commit-ის მოკლე id, თავისით იცვლება). აგების კოდით ადვილია იმის შემოწმება, რომ ტელეფონზე ზუსტად უახლესი ვერსიაა.

## გამოშვება

`.github/workflows/deploy.yml` ყოველ `main`-ში ატვირთვაზე ტესტავს, აგებს და GitHub Pages-ზე ათავსებს.

ერთხელ საჭიროა:
1. რეპოზიტორია → **Settings → Pages → Source: GitHub Actions**.
2. იგივე გვერდზე **Custom domain**: შენი ქვედომენი.
3. DNS-ში ქვედომენზე `CNAME` ჩანაწერი → `datokiki777.github.io`.

აპი გათვლილია დომენის ძირზე (`base: '/'`), ამიტომ ცალკე ქვედომენი სწორი არჩევანია. ცალკე origin ნიშნავს, რომ ნოტების ბაზა სხვა აპებისგან გამოყოფილია.
