- ტექსტური ნოტები და ჩეკლისტები (ერთიდან მეორეში გადაყვანა)

- ბექაპი JSON ფაილით, ჯგუფებიანად (ჩამოტვირთვა და აღდგენა, ახალი/ძველი ვერსიის გაერთიანებით; ძველი ფორმატის ფაილებიც იკითხება)

## ტექნოლოგიები

React 19 · TypeScript · Vite · vite-plugin-pwa (Workbox) · Dexie (IndexedDB) · react-router (HashRouter) · i18next · Zustand · CSS Modules · Vitest

## სტრუქტურა

```
src/
  app/            აპის გარსი: routes, ქვედა ნავიგაცია, თემა, განახლების შეტყობინება
  core/           საერთო ნაწილი, ფუნქციებზე დამოუკიდებელი
    db/           Dexie ბაზა და სქემის ვერსიები
    i18n/         ენები (languages.ts + locales/*.json)
    settings/     პარამეტრები (ენა, თემა, ხედი), localStorage-ში
    ui/           პატარა საერთო კომპონენტები
  features/       თითო ფუნქცია = ერთი საქაღალდე
    notes/        მოდელი, repository, სელექტორები, კომპონენტები, გვერდები
    groups/       ჯგუფების მოდელი, repository, ზოლი (GroupStrip), ჯგუფის ფურცლები
    backup/       ბექაპის ფორმატი და აღდგენა
    settings/     პარამეტრების გვერდი
```

წესები, რომ აპი გაფართოვდეს და არ დაიბნეს:

- **ბაზასთან მხოლოდ `repository` საუბრობს.** კომპონენტები `db`-ს პირდაპირ არ ეხებიან (`features/notes/repository.ts`).
- **სუფთა ლოგიკა ცალკეა** (`model.ts`, `selectors.ts`): ფილტრი, დახარისხება, ვალიდაცია. ტესტებით დაფარულია.
- **ფუნქცია არ იმპორტირებს სხვა ფუნქციას**, მხოლოდ `core`-ს. გამონაკლისები: `groups` და `backup` იყენებენ `notes`-ს (ის ძირითადი ფუნქციაა).
- **ბაზის ცვლილება = ახალი `this.version(n)`** `core/db/db.ts`-ში. ძველ ვერსიას ხელს არ ვუხლებთ. ვერსია 2 (ჯგუფები) უკვე ასე დაემატა და ძველ ნოტებს `groupId = null` ენიჭებათ; ეს ტესტითაა დაფარული.

## ახალი ენის დამატება

1. დააკოპირე `src/core/i18n/locales/en.json` → `locales/<კოდი>.json` და თარგმნე.
2. `src/core/i18n/languages.ts`-ში დაამატე ერთი ხაზი.

პარამეტრებში ენის არჩევანი თავისით გაჩნდება.

## სინქრონიზაციისთვის მომზადებული ადგილები

- ყველა ჩანაწერს აქვს UUID (`id`), `createdAt`, `updatedAt` და `deletedAt`.
- წაშლა ჯერ მხოლოდ ნიშნავს ჩანაწერს (`deletedAt`), რაც მერე tombstone-ად გამოდგება.
- `repository.importMany` უკვე აერთიანებს ჩანაწერებს `updatedAt`-ით: უახლესი იგებს. იგივე წესი გამოგადგება ღრუბელთან გასაერთიანებლად.
- ფიზიკური წაშლა (`deleteForever`, `emptyTrash`) სინქრონიზაციის დამატებისას tombstone-ით უნდა შეიცვალოს (მონიშნულია კოდში).
- დაშიფვრა (end-to-end) ცალკე გადაწყვეტილებაა, სანამ ნოტებს ღრუბელში ვინახავთ.

## ანგარიში და სინქრონიზაცია (Firebase)

Firebase პროექტი: `todo-f1950` (Authentication: ელფოსტა/პაროლი; Firestore: europe-west3; უფასო Spark გეგმა, Blaze/ბარათი არ არის მიბმული). კონფიგურაცია `src/core/firebase/config.ts`-შია (ეს საჯარო იდენტიფიკატორებია და არა საიდუმლო), მონაცემებს წესები იცავს: `docs/firestore.rules`.

გეგმა სამ ეტაპად: **1) ანგარიშით შესვლა: Google (მთავარი) და ელფოსტა/პაროლი** (გაკეთებულია, ნამდვილი Google-ით შესვლა ტელეფონზე უნდა შემოწმდეს) · 2) ნოტებისა და ჯგუფების სინქრონიზაცია · 3) 30-დღიანი დღიური ასლები და აღდგენა.

Firebase-ის კოდი ცალკე ფაილად იტვირთება და მხოლოდ საჭიროებისას. ტესტისთვის არსებობს ყალბი შესვლა: `VITE_FAKE_AUTH=1 npx vite build` (რეალურ აგებაში ის არ ხვდება).

## ვერსია

Settings → "აპის შესახებ" აჩვენებს ორ რამეს: **ვერსიას** (`package.json`-ის `version`, ხელით იცვლება ყოველ გამოშვებაზე) და **აგების კოდს** (git commit-ის მოკლე id, თავისით იცვლება). აგების კოდით ადვილია იმის შემოწმება, რომ ტელეფონზე ზუსტად უახლესი ვერსიაა.

## გამოშვება

`.github/workflows/deploy.yml` ყოველ `main`-ში ატვირთვაზე ტესტავს, აგებს და GitHub Pages-ზე ათავსებს.

ერთხელ საჭიროა:
1. რეპოზიტორია → **Settings → Pages → Source: GitHub Actions**.
2. იგივე გვერდზე **Custom domain**: შენი ქვედომენი.
3. DNS-ში ქვედომენზე `CNAME` ჩანაწერი → `datokiki777.github.io`.

აპი გათვლილია დომენის ძირზე (`base: '/'`), ამიტომ ცალკე ქვედომენი სწორი არჩევანია. ცალკე origin ნიშნავს, რომ ნოტების ბაზა სხვა აპებისგან გამოყოფილია.
